# 项目经验

这个项目从"手环 11 的动态表盘该怎么做"到"Win + 安卓双端一键工具"，
中间踩了不少坑。这里把有复用价值的结论整理出来。

分四部分：**技术结论**、**三个真实 bug 的根因**、**方法论**、**AI 协作复盘**。

---

## 一、技术结论（可复用的部分）

### 1. 官方链路的核心依赖是可以绕开的

官方做法是：装 Vela IDE → 手写 Lua/XML → 跑 `Compiler.exe` 打包。

其中 `Compiler.exe` 看起来是绕不过的黑盒，但它只是一个**把已知输入格式化成已知输出格式**的
打包器。一旦把输出格式（`.face`）逆向清楚，就可以用任何语言自己拼装。

**实际收益：**

- 摆脱 **x86 Windows 依赖** → 安卓能直接生成表盘
- 摆脱 **授权不明的第三方二进制** → 项目可以开源分发

**推广一下**：遇到"必须用某个官方工具/闭源二进制"的场景，先问一句
——它是**在计算**，还是只是在**格式化**？后者通常可以直接实现。

### 2. 优化前先找到「主杠杆」

调表盘体积时，直觉是"压缩率越高越小"，于是第一反应去调色深。

实测：**色深从 P256 压到 P64，每帧只降 38%。**
而**帧率从 24 降到 12，体积直接减半。**

两个量级完全不同的杠杆，但在参数面板上看起来是平级的。
**这就是为什么"实时体积预估"是这个工具最重要的功能** ——
它让杠杆的大小变得可见，而不是靠猜。

> 教训：做参数化工具时，**不要让用户凭直觉判断哪个参数重要**。
> 把结果实时算给他看。

### 3. 固定开销会让优化撞墙

`.face` 有 431 KB 的固定尾部位图开销。当帧数降到 15 帧时，
它占总体的 41% —— 此时再怎么压色深，收益都极其有限。

**推广**：优化前先量清楚「不可优化的固定部分」占多少。
如果固定部分已经是主导项，继续优化可变部分就是浪费。

### 4. 有损压缩的损失是「有方向」的

PNG 量化损失的是**色深**（表现为色带）；
JPEG 损失的是**高频细节**（表现为噪点/块效应）。

两者体积相同时，观感差异取决于**内容类型**：

- 渐变多的真人照片 → 色带最刺眼 → 用 JPEG
- 色块清楚的动漫平涂 → 噪点最刺眼 → 用 PNG

**没有"哪个更好"，只有"哪个的缺点在当前内容上更不明显"。**

### 5. 「息屏显示」不是表盘的一个图层，而是同级子工程

直觉上会以为 AOD（息屏显示）是同一套资源里的一个"状态"，
改改 `Screen` 数量、加一段 Lua 分支就行。

实测不是。官方 LEP 工程里 `AOD/` 和根目录**平级**：

```
<工程>/
├── <表盘名>.fprj        ← 主屏（Lua + 一个透明挂载点）
└── AOD/
    ├── AOD.fprj         ← 息屏屏（纯控件 XML，零 Lua）
    └── images/
```

只有**主屏**能用 Lua。AOD 屏连编译都不单独跑一遍 —— 它是被主工程
一起打包进同一个 `.face` 的，且 AOD 里挂 Lua 会被编译器静默丢弃。

**关键连锁反应**（这些是"没量过就一定会踩"的）：

| 项 | 无 AOD | 有 AOD |
|---|---|---|
| header 屏数 | 1 | 2 |
| 索引表起点 | `272` | `360` |
| 索引表后紧跟的内容 | 1 条哨兵（16 B） | 多组按 tag 分组的描述块 |

所以 **任何按"索引表永远从 272 开始、哨兵永远紧跟其后"写的解析器，
遇到 AOD 产物就会崩或者解析错**。本项目的 `tools/verify_face.py`
第一版就是这么挂掉的，后来改成按格式不变量扫描候选起点。

> 推广：遇到"看起来是同一层的东西"，先去目录结构里确认它到底在哪一层。
> **层次搞错，后面所有推导都建立在错误的边界上。**

### 6. 证伪要证到「能证的程度」

"表盘点击跳转到系统 App"这个需求，最终结论是**做不到**。

但"做不到"分两种：一种是"我没找到方法"，一种是"这个平台不支持"。
前者不能写进文档当结论 —— 用户下次换个人问，可能就被否掉了。

真正的证据链是**五款结构完全不同的官方表盘**（不同开发者、不同表盘类型、
不同交互设计），产出的 `.fprj` 里**没有任何一个含跳转声明**，且
Lua 侧也没有对应的 API。再加上官方 `smash.lua` 这种交互最复杂的样例里
同样没有 —— 这才能把结论从"我没找到"推到"这平台没有"。

**成本对比**：多做 4 组对照实验大概半天，但省掉的是"用户按你的话去试、
失败、回来质疑"的一轮返工。

反过来也一样：本项目里"miwear 支不支持 JPEG 解码"这种问题，
**一次真机验证就能定论**，就不该靠推理论证。

> 判断标准：**结论要写进对外文档 / 要别人基于它做决策时，就值得把证据补齐。**

## 二、真实 bug 的根因

### Bug 1：裁剪框"缩放不跟手"

**现象**：拖动框体正常，但拖角点缩放时手感极差 —— 松手回弹、感觉"没跟上鼠标"。

**根因**：

```python
# 错误写法
new_h = origin.height() + dy
```

- `dy` 是**本次鼠标移动的增量**（一个很小的值）
- `origin.height()` 是**按下那一刻的高度常量**

两者混用 → 每一次移动事件都在**从初始值重新算一遍**，增量根本没被累积。
所以框的尺寸只在"初始值 ± 一次微小增量"之间抖，怎么拖都不长大。

拖动框体为什么正常？因为它用的是**增量累加**：

```python
new_pos = current_pos + dy     # 每一步都基于当前位置
```

**修复**：缩放也改成绝对定位驱动 —— 以按下时刻的左上角为锚点，
根据当前鼠标位置直接算出目标尺寸：

```python
anchor = self._origin.topLeft()
h_from_y = cur.y() - anchor.y()
h_from_x = (cur.x() - anchor.x()) / ASPECT
new_h = max(self._MIN_H, max(h_from_y, h_from_x))
```

同时横向、纵向拖动都能响应（取两者较大值），斜向拖也自然。

> **教训**：交互逻辑里，**"当前状态 + 增量"和"锚点 + 绝对位置"是两种范式，不能混用**。
> 混用的症状很典型：操作"跟手"但不累积，或者累积但会漂移。

### Bug 2：JPEG 表盘"质量很差"

**现象**：JPEG 版能正常显示，体积也确实小很多，但画面糊、彩色边缘串色。

**排查过程**：

1. 先怀疑是质量参数（q80）太低 → 调到 q90，体积涨了 48%，但**亮度 PSNR 只涨 3.6 dB**，
   观感改善不明显。这说明**问题不在量化精度**。
2. 改用**分通道 PSNR**（Y / Cb / Cr）重新测 → 发现色度指标明显偏低：
   `Cb 41.87 dB` vs 亮度 `36.35 dB` —— 等等，色度看起来更高？
   不对，要看的是**同一档位下不同子采样设置的对比**：

   | | 每帧 | Y | Cb | Cr |
   |---|---|---|---|---|
   | q80 4:2:0 | 23.2 KB | 36.35 | 41.87 | 38.96 |
   | q80 4:4:4 | 27.5 KB | 36.36 | **44.34** | **41.62** |

   同样 q80，关掉子采样后 **Cb/Cr 涨了 2.5 dB，而亮度几乎没动** ——
   这就锁定了：**损失全在色度上**。
3. 根因确认：PIL 不显式指定 `subsampling` 时落到 libjpeg 默认的 **4:2:0**，
   把 212×520 的色度平面砍到 **106×260**（面积 1/4）。小图上这个损失非常显眼。

**修复**：`subsampling=0`（4:4:4），只多 19% 体积。

> **教训 1**：**单看亮度 PSNR 会漏掉整类问题。** 色度子采样、色度偏移这类缺陷
> 在亮度指标上完全隐形。
>
> **教训 2**：**先确认问题在哪一层，再调参数。** 我一开始去调 quality，
> 是在错误的维度上努力 —— 真正的瓶颈在子采样。
>
> **教训 3**：安卓端 `Bitmap.compress` 固定 4:2:0 **无法修改**。
> 遇到平台限制时，正确做法是**明确告知用户天花板在哪**，而不是假装能解决。

### Bug 3（认知 bug）："为什么只有 46 帧，你裁时长了吗？"

**背景**：早期有个表盘产出 3.16 MB / 46 帧，我描述成"压缩得更强"。
用户追问：**"你裁剪视频时长了吗？"**

**复核结果：没有裁时长。是我描述错了。**

原始链路其实是：

```
源 8s / 192 帧 / 24fps
  → 降采样到 48 帧（覆盖完整 8 秒）
  → 删 2 帧得 46 帧（3.44 MB）
  → period = 42 ms
  → 播放 1.92 秒，即 4.17 倍速
```

当时的源视频已经不在盘上，只能靠**帧内容交叉验证**：

1. `video-frames/`（16 帧）与 `video-frames-48/`（48 帧）的**首帧差异 = 0.0** → 都从第 0 帧起
2. 48 帧版的末帧与 16 帧版的**末帧差异最小（2.38）**，而不是与第 4 帧最小（8.06）
   → **48 帧覆盖的是完整 8 秒**，不是前 2 秒
3. 相邻帧平均差异比 ≈ 3.64 ≈ 抽帧间隔比 12:4 → 确认是**每 4 帧取 1 帧**

所以：**素材是"主体静止的微动视频"，加速 4 倍也看不出来**，
这个"快放"一直没被发现，而我把它误读成了"压缩更强"。

**这个 bug 的直接产物**：工具里加了「保持帧率、压缩时长（快放）」开关 ——
把「流畅度 × 时长 × 体积」这个原本隐式的权衡**显式暴露给用户**。

> **教训**：**描述结果时不要用因果词包装未经确认的归因。**
> 我说"压缩更强"时，其实只是在"体积更小"这个现象上贴了一个我猜测的原因。
> 正确说法是"体积更小，原因是帧数少"——然后自然就会有人问"帧数为什么少"。

### Bug 4：安卓端末端"少 2 字节"—— 对齐规则只对了一半

**背景**：把 `.face` 打包器从 Python（`face_builder.py`）重写成纯 Java（`FaceBuilder.java`），
拿真实 `Compiler.exe` 产物做逐字节差分。前几个样本全过，到 `n12.face` 突然差 2 字节。

**排查**：

```
n=1/2/3/5   ✅ 字节一致
n=8         ✅ 字节一致
n=12        ❌ 首个差异 @32（头部「文件数据区结束」字段），Java 少 2
```

差异在头部而不是内容里，说明**长度**算错了，不是数据写错了。

**根因**：实现里只给"文件项之间"补了对齐 padding，**最后一条没有补**。
直觉是"末尾不用对齐"，但数据区结束位置 `filesEnd` 是下一段（尾部位图 / AOD 素材区）的起点，
实测它必须落在 4 字节边界上。

关键证据来自一个**专门设计的对齐探针**：把最后一个文件的名字长度从 0 走到 3，
让「末条长度 % 4」遍历所有余数，再量真实素材区起点：

```
pad=1 → 末条原始结束 3001，4 字节对齐后 3004，实测素材区起点 3004   → 规则是 4 不是 2
```

**修复**：不再写"循环后再补 padding"，而是把对齐合进游标推进：

```java
int cur = descEnd;
for (int i = 0; i < n; i++) cur = align4(cur + size[i]);
final int filesEnd = cur;        // 已对齐，直接作为素材区起点
```

> **教训 1**：**"n=8 过了"不等于"对齐规则对了"。** n=8 的末条长度碰巧余 0，
> 这个样本对这个变量**完全不敏感**。样本集必须让被测长度遍历 0/1/2/3。
>
> **教训 2**：**"末尾可以不管"是一种值得单独验证的直觉。**
> 凡是被当作"下一段起点"的位置，都要问一句"它对齐吗"。

### Bug 5：`firstRecOff()` 返回相对偏移 —— 所有 AOD 样本错得一模一样

**现象**：AOD 分支一跑，**每一个**样本都在 `@276` 附近与参考产物差一大截，
而且差值完全相同。看起来像"整段布局都错了"，实际上只是一个常量性质的问题。

**根因**：需要"某 tag 的第一条描述记录在哪"，写了个辅助函数：

```java
// ❌ 返回的是"第 k 条"这个序号 × 16，即相对偏移
static int firstRecOff(List<Rec> recs, int tag, int d0) { ... return k * 16; }
```

调用方拿它当**绝对偏移**用（写进描述记录、算素材区起点）。
差的那一截正好是 `d0`。

**修复**：让函数返回 `d0 + k * 16`，并在签名注释里写明"返回绝对值"。

> **教训**：**"偏移"这个词在同一个文件里同时表示绝对和相对时，一定会出事。**
> 要么函数名带 `abs`/`rel`，要么类型上分开。
> 症状特征也值得记住：**所有样本错得一模一样 → 先找常量性质的问题，别去查数据**。

### Bug 6：只测一种样本，三个分支永远没被执行

这是 Bug 4/Bug 5 的共同放大器。重写过程中实际存在**至少三个"只在特定样本上才执行"的代码路径**：

| 路径 | 只有什么时候会走到 | 漏测的后果 |
|---|---|---|
| 无 AOD 的元数据尾（3 槽，`[260]=0,[264]=d0,[268]=16`） | 只有生成**不带 AOD** 的产物时 | 打包器无条件写 25 槽 AOD 尾 → 产物**多 88 字节**，索引表起点/头部/预览位置全偏 |
| 文件数用 u32 读 | 只有文件数 > 255 时（多壁纸 ≈ 1920） | 单字节读成 `N % 256` → 索引表定位全错，报"重建失败"而不是"文件数读错" |
| 末条补对齐 | 只有末条长度 % 4 ≠ 0 时 | 见 Bug 4 |

而且**两份实现是逐行照抄的**（Python 一份、Java 一份），
所以"读同一份逻辑"根本不能证明什么 —— 只有**各自跑真实产物、逐字节对比**才算数。

> **教训**：**差分测试的样本集要按"能触发哪些分支"设计，不是按"看起来正常"挑。**
> 具体做法：把每个 `if` 都列出来，每个分支至少给一个样本。
> 本项目最终建成的样本集是：无 AOD 的 7 个（帧数 1/2/3/5/8/12 + 一个 16 字节的边界产物）、
> AOD 的 6 个（空/时间/时间+日期/黑底/大字号/自定义色），外加 Lua 12 例、AOD 计划 12 例、
> 颜色解析 12 例 —— **全部逐字节或逐字段一致才敢说"移植完成"**。

## 三、方法论

### 1. 用「同一批帧 + 不同 period」把耦合拆开

帧数、时长、流畅度看起来是三个绑死的量（帧数 = 时长 × 帧率）。
但实际做的时候发现：**抽帧和播放节奏是两件独立的事**。

生成的 `main.lua` 里只有一个 `period` 字段控制播放节奏，
帧图片本身完全一样。所以：

| | 抽帧 | period | 结果 |
|---|---|---|---|
| 保时长 | N 帧摊满整段 | 降低后的帧率 | 时长不变、掉帧 |
| 保帧率 | N 帧摊满整段 | 目标帧率 | 流畅、变快 |

**验证方式**：两种模式生成的 `.face`，PNG 帧数据**字节级完全一致**，
只有 `main.lua` 里一个数字不同。

> **推广**：当三个量看起来必须绑死时，去找**把其中两个解耦的那个中间层**。
> 这里就是"抽帧"和"播放"之间那个 `period`。

### 2. 逆向：从「差异」而不是从「整体」入手

分析 `.face` 格式时，有效的手段是**构造差异**：

- 改表盘 ID → 观察哪些字节变了
- 改帧数 → 观察哪些字段跟着动
- 用单色图帧 → 数据区长度可预测，容易定位偏移

而不是盯着一个完整的二进制文件发呆。

### 3. 把「不可复现的结论」变成「可复现的脚本」

所有体积/画质数字都写成了脚本（`tools/bench_quality.py`），
所有格式结论配了检查器（`tools/verify_face.py`）。

理由很简单：**数字会过期**。换了 PIL 版本、换了 libjpeg 编译选项，
4:2:0 的默认行为都可能变。有了脚本，结论失效时能立刻发现。

### 4. 生成的代码也要能被静态检查

`main.lua` 是**字符串拼出来的** —— 参数一多，就必然会出现
"某个组合下变量名拼错 / 引用了还没声明的函数"这类只在运行时炸的问题，
而手环上跑崩是看不到报错的。

所以加了 `tools/lint_lua.py`：穷举
**壁纸数（1/2/3）× 对齐（9 种）× 点击行为（4 种）× 时间日期开关（4 种）**
共 435 种组合，每种都真生成一遍 `main.lua`，再用 `luaparser` 做语法解析。

这条抓到的不是语法错误，而是**作用域错误**：
点击行为里的 `anim` 分支会调用 `pauseAll()` / `resumeActive()`，
但这两个是 `local function`，如果拼接顺序不对（声明块排在调用块之后），
Lua 不报错，只是把它们捕获成 `nil` —— 点一下表盘就静默失效。

> **推广**：只要产出物是"代码这一类的文本"，就应该有个"能不能解析"的门槛。
> 语法检查器的成本很低，但它拦下的是**手工肉眼看 435 种组合根本看不出来**的东西。

### 5. 跨语言重写：「照抄一致」什么都不能证明，只有差分能

把算法从 Python 搬到 Java（安卓端移植）时，很容易有一个错误的安全感：
**"我是逐行照抄的，逻辑一样，所以结果一样。"**

这个项目里被证明是错的。实际的差距来源：

| 差距来源 | 例子 | 只看代码能发现吗 |
|---|---|---|
| 语言默认值不同 | Python 里 `bytes` 切片 vs Java 里 `byte[]` 下标，一处 `+1` 之差 | 要逐行数下标，很难 |
| 同名不同义 | `size` 一边指"含 padding"、一边指"不含" | 不会 |
| 未执行的分支 | Java 版有个分支从没编译过（`asset.size()`，`asset` 是数组没有这方法） | 编译器能发现 —— **前提是你真的编译过** |
| 辅助函数的返回值语义 | `firstRecOff` 返回相对偏移，调用方当绝对用 | 不会 |

**可靠做法是三道门槛，缺一不可：**

1. **真实产物当 oracle，不用手写期望值。**
   参考实现要跑**官方 `Compiler.exe` 的真实输出**，而不是"我认为应该长这样"。
   手写的期望值只能验证"我理解对了"，验证不了"实现对了"。
2. **逐字节对比，不要比"关键字段"。**
   比 `size`/`offset` 会漏掉对齐、padding、元数据槽数这类"边角 88 字节"的问题 ——
   而恰恰是这些让产物不可用。本项目的做法是把产物解析→规范化→对拍，
   任何一处不同就打印首个差异偏移。
3. **样本集按"能触发哪些分支"设计。**
   见 Bug 6 的表：每个 `if` 至少一个样本。
   "挑几个看起来正常的样本跑通"是最典型的假阳性来源。

> **推广**：只要同一份逻辑存在**两份以上实现**（跨语言、跨版本、参考实现 + 优化实现），
> 就必须有一个**自动化的差分回归**，并且这个回归要进仓库、跟着代码走。
> "我核对过了"不是资产，"能随时重跑的对比脚本"才是。
>
> **本项目欠账**：这一轮移植用的差分脚本（Python oracle 生成 + JVM 侧调用同一份
> `core/face` 代码生成，再逐字节对拍）跑在**会话临时目录**里，**没有随仓库发布**。
> 上面那 7/7、6/6 的等价性结论是真的（12 份样本，含 AOD），
> 但目前**无法只靠仓库重跑** —— 这是已知缺口，不是"已经做到"。

## 四、AI 协作复盘

本项目在开发过程中大量使用了 AI 协助（详见 README 的[关于 AI 协助](../README.md#关于-ai-协助)）。
作为一次比较深入的实践，记录一下哪些地方有效、哪些地方容易出问题。

### 有效的地方

| 场景 | 为什么 AI 有效 |
|---|---|
| **格式逆向** | 逐字节对比、模式匹配、假设验证是"高密度重复劳动"，AI 不容易累也不会跳步 |
| **双端移植** | Python ↔ Java 的逐字节等价实现，交给 AI 做一致性最高（两份 FaceBuilder 就是这么来的） |
| **构建脚本** | 无 Gradle 的 aapt2/d8/zipalign/apksigner 链路，属于"知道就能写、不知道就搜半天"的知识 |
| **文档** | 把散落的实测数据整理成结构化文档，AI 效率远高于手工 |
| **测量脚本** | 分通道 PSNR 这类脚本，写起来繁琐但逻辑直白 |

### 容易出问题的地方

**1. 归因会被"包装"成因果。**

Bug 3 就是典型案例：AI（我）看到"体积变小"，就直接说成"压缩更强"。
现象是真的，**原因是我猜的，而且猜错了**。

> **对策**：对 AI 给出的因果解释保持警惕。区分「观测到的现象」和「对现象的解释」，
> 后者要求提供证据（这里是帧内容交叉验证）。

**2. 描述性的措辞可能与代码行为不一致。**

Bug 3 之后才暴露出：工具文档写的是"保时长"，而早期那个表盘实际是"快放" ——
**两者语义完全相反**。用户按文档理解，就会得出错误结论。

> **对策**：文档和代码必须交叉验证一次。本项目里有明确脚本背书的数字只有两类 ——
> 体积/画质（`tools/bench_quality.py`）和格式结构（`tools/verify_face.py`）。
> 其余数字（AOD 逐项开销、帧数-体积曲线）来自一次性差分实验，
> 文件与结论记在 [体积与画质实测](体积与画质实测.md)，**没有随仓库发布可重跑的脚本** ——
> 引用这类数字时要意识到这一点。

**3. AI 会顺着用户的假设走。**

用户说"压缩到 3.5MB 只有 46 帧，你裁时长了吗"，
如果当时我顺着"可能裁了"去解释，就会编出一套看似合理的说法。
实际是去查了帧内容才确认没裁。

> **对策**：涉及事实核查的问题，**要求可验证的证据链**，不要接受叙事化的解释。

**4. 平台限制容易被"假装解决"。**

安卓的 `Bitmap.compress` 固定 4:2:0，这是个死路。
但 AI 有可能给出"用 XXX 参数就能改"这类听起来合理、实际不存在的方案。

> **对策**：平台相关的 API 行为，**以官方文档 + 实测为准**，
> 不接受"应该可以"这类表述。本项目最后的处理是——如实写明这是平台限制，
> 并说明安卓端质量天花板低于 Windows 端。

### 一条总结

**AI 适合承担"执行密度"和"知识检索"，不适合承担"事实裁定"。**

凡是"事实是什么"的问题（这个数是不是真的、这个 API 到底行不行、
这个结论能不能复现），都要有独立的验证路径。
本项目的做法是：**关键结论优先做成能重跑的脚本**（`tools/` 下三个），
没做到的那部分（AOD 逐项开销、双端差分回归）在本文件里**明确标注为欠账**。

这也是为什么 `tools/` 目录和文档同等重要 ——
它们不是"可选的补充材料"，而是结论本身的一部分。
**反过来说，凡是 `tools/` 里没有对应脚本的数字，读的时候都要降一档信任。**
