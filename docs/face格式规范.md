# `.face` 二进制格式规范

本文档记录小米手环 11 动态表盘文件 `.face` 的二进制布局。

**这份规范是通过对比官方编译器 `Compiler.exe` 的输入输出、逐字节分析其产物得出的，
不是官方文档。** 它在本项目对应的固件/工具链版本上实测有效，换版本不保证仍然成立。

所有多字节整数均为**小端序（little-endian）**。

> 参考实现（两份逐字节等价的独立实现）：
>
> - Python：`watchface-tool/watchface_tool/face_builder.py`
> - Java：`watchface-android/core/face/FaceBuilder.java`
>
> 想验证一份 `.face` 是否符合本规范，直接跑 `tools/verify_face.py`。

---

## 1. 整体布局

```
偏移          长度                 内容
──────────────────────────────────────────────────────────────
[0, 64)       64 B                 文件头
[64, 172)     108 B                Title 区
[172, 272)    100 B                元数据区
272 起        (N+1) × 16 B         索引表（含 1 条哨兵）
↑ 索引表结束 = 文件数据区起始
              ...                  文件数据区（各文件项，4 字节对齐）
              ...                  尾部位图（212×520 RGBA8888）
```

`N` = 文件数（帧图片数 + 1 个 `main.lua`）。

---

## 2. 文件头 `[0, 64)`

| 偏移 | 长度 | 值 | 说明 |
|---|---|---|---|
| 0 | 4 | `5A A5 34 12` | magic |
| 4 | 1 | `0` | 固定 |
| 5 | 1 | `10` | **表盘 ID 的长度** |
| 6 | 10 | 0 | 填充 |
| 16 | 4 | `0x00000800` | 固定常量 |
| 20 | 8 | 0 | 填充 |
| 28 | 4 | `1` | 固定 |
| 32 | 4 | `data_end` | **文件数据区的结束偏移**（= 尾部位图起始） |
| 36 | 4 | 0 | 填充 |
| 40 | 10 | ASCII | **表盘 ID**（不足补 `\0`） |
| 50 | 14 | 0 | 填充 |

### ⚠️ 坑：`[4]` 和 `[5]` 是两个独立字节

`[5]` 是 ID 长度（单字节），**不是** `uint16` 的一部分。

如果把 `[4..5]` 当成一个小端 `uint16` 来写（即写成 `0x0A00`），
整个文件会从第 4 字节开始**整体错位 1 字节**，产物无法被识别。
这个坑在早期实现里踩过。

---

## 3. Title 区 `[64, 172)`

| 偏移 | 长度 | 说明 |
|---|---|---|
| 64 | 40 | 填充 |
| **104** | **16** | **Title 字段**（ASCII，null 结尾） |
| 120 | 52 | 填充 |

### ⚠️ 坑：Title 是**固定 16 字节**

不是 12 字节，也不是变长。写成 12 会整体错位。

## 4. 元数据区 `[172, 272)`

| 偏移 | 值 | 说明 |
|---|---|---|
| 172 | `data_end` | 文件数据区结束偏移 |
| 176 | `1` | 固定 |
| 180 | `256` | 固定 |
| 184 | `0` | 固定 |
| 188 | `INDEX_START` (272) | 索引表起始 |
| 192 | `0` | 固定 |
| 196 | `INDEX_START` | 同上 |
| 200 | `0` | 固定 |
| 204 | `INDEX_START` | 同上 |
| 208 | `0` | 固定 |
| 212 | `INDEX_START` | 同上 |
| **216** | **`N`** | **文件数（u32，不是单字节！）** |
| 220 | `INDEX_START` | 同上 |
| 224 | `0` | 固定 |
| 228 | `idx_end` | 有效索引表结束 = `272 + N × 16` |
| 232 | `0` | 固定 |
| 236 | `idx_end` | 同上 |
| 240 | `0` | 固定 |
| 244 | `idx_end` | 同上 |
| 248 | `0` | 固定 |
| 252 | `idx_end` | 同上 |
| 256 | `0` | 固定 |
| 260 | `0` | 固定 |
| **264** | **`idx_end`** | 同上 |
| **268** | **`16`** | **索引表条目大小** |

> 注意 `idx_end = 272 + N × 16`，**不含哨兵那一条**；
> 而数据区实际起始是 `272 + (N+1) × 16`（含哨兵）。

### ⚠️ 两个「只在特定样本上才暴露」的坑

**① `[216]` 的文件数是 u32，不是单字节。**

单张壁纸最多 96 帧，用 `d[216] & 0xFF` 读也碰巧读对；
但**多壁纸**一上来就会 >256 帧（8 张 × 240 帧 = 1920），此时单字节解析会静默读成
`N % 256`，索引表定位全错，报的是"重建失败"而不是"文件数读错"。正确写法：

```python
n = struct.unpack_from("<I", d, 216)[0]
```

**② 元数据区尾部长度取决于有没有 AOD。**

| | 元数据区范围 | `[260]` | `[264]` | `[268]` |
|---|---|---|---|---|
| 无 AOD | `[172, 272)`，**3 个有效槽** | `0` | `d0` | `16` |
| 有 AOD | `[172, 360)`，25 个有效槽 | — | — | — |

打包器如果**无条件**写 25 槽的 AOD 尾，产物会比正确值**多 88 字节**，
而且索引表起点、头部 `[32]`、尾部预览位置全部随之偏移。
两份实现（Python / Java）只测 AOD 样本时，这个分支永远不会被执行到 —— 见「项目经验」。

## 5. 索引表 `272` 起，`(N+1) × 16` 字节

每条 16 字节：

| 偏移 | 长度 | 字段 |
|---|---|---|
| +0 | 2 | `index`（从 0 递增） |
| +2 | 2 | `0x0500`（固定标记） |
| +4 | 4 | `0`（保留） |
| +8 | 4 | `offset`（该文件项在文件中的绝对偏移） |
| +12 | 4 | `size`（见下） |

### ⚠️ 关键：`size` 的计算方式

```
size = 20 + len(文件名) + len(数据)
```

- `20` = 文件项描述头的长度（3 + 1 + 16）
- **`size` 不包含末尾的 4 字节对齐 padding**

这一点很反直觉，但实测如此。写成含 padding 的值会导致数据区偏移计算全部错乱。

### 哨兵条目

索引表最后**额外多一条**，内容为：

```
index = N - 1      （重复最后一条的 index）
0x0500
0
offset = 0
size   = 0
```

> ⚠️ 这支哨兵**紧跟在索引表后面**，只在**没有 AOD 子工程**时成立。
> 带 AOD 时这段会变成一个多组的描述块，哨兵被挤到最后 ——
> 索引表起点也从 `272` 挪到 `360`。详见第 11 节。

## 6. 文件项（数据区）

每个文件项的布局：

| 长度 | 内容 |
|---|---|
| 3 B | **数据大小**（小端，只取低 3 字节 = 最多 16 MB） |
| 1 B | **文件名长度** |
| 16 B | 全零 |
| `文件名长度` | 文件名（ASCII） |
| `数据大小` | 文件内容 |
| 0~3 B | **4 字节对齐** padding |

其中 padding 长度为：

```python
pad = (4 - size % 4) % 4     # size = 20 + len(名) + len(数据)
```

### ⚠️ 坑：4 字节对齐是硬性的，**包括最后一条**

不对齐会在数据区里留下 1/2/3 字节的 gap。这是**手工拼装失败最常见的原因** ——
产物能被解析，但内容是错位的。

**而且最后一条也要 pad。** 直觉上"末尾不用对齐了"，但数据区结束位置 `filesEnd`
是下一段（尾部位图 / AOD 素材区）的起点，实测它**必须落在 4 字节边界上**：

```
实测（对齐探针 `aln_probe.py`，把最后一个文件的名字长度从 0 走到 3）：
  pad=1 → 末条原始结束 3001，4 字节对齐后 3004，真实素材区起点 3004   ✅
```

只取 2 字节对齐会在帧数多时暴露：n=8 帧的样本碰巧通过，n=12 帧的样本差 2 字节
（首个差异出现在头部 `[32]` 数据区结束位置）。**因此样本集必须让"被测长度 % 4"遍历 0/1/2/3**，
只测一两个样本是抓不到的。

> 打包器的正确形态是把对齐和赋值合并，别用"循环结束后再补一段 padding"的写法：
> ```python
> cur = descEnd
> for i in range(n):
>     cur = align4(cur + size[i])
> files_end = cur          # 已对齐，直接作为下一段起点
> ```

### 文件名规则

- 前缀是 **`lua/`**，不是 `app/lua/`。
  例如 `lua/face_01.png`、`lua/face_02.png`、`lua/main.lua`。
- 帧名从 **`face_01`** 开始（1-based），不是 `face_00`。
- 扩展名必须与 `main.lua` 里引用的**完全一致**。
  改了编码格式（PNG ↔ JPEG）而没同步 Lua，表现是**手环上黑屏**。

## 7. 尾部位图

紧跟在数据区之后，**没有偏移索引指向它**，只能靠前面的数据累加算出来。

| 长度 | 内容 |
|---|---|
| 4 B | 全零 |
| 2 B | 宽度 u16（= 212） |
| 2 B | 高度 u16（= 520） |
| 4 B | 位图字节数（= 440 960） |
| 440 960 B | RGBA8888 像素数据 |

### ⚠️ 固定 431 KB，与帧数无关

`212 × 520 × 4 = 440 960` 字节（431 KB）。这是**表盘选择器里显示的静态预览图**，
大小由屏幕分辨率决定，**不随动画帧数变化**。

后果：**帧数很少时，这部分开销可能比全部帧数据加起来还大。**
所以"把几十帧的表盘再压小"是不可能的 —— 431 KB 是硬地板。

早期曾误以为它能缩小（格式上宽高是 u16 字段），但实测官方产物就是 212×520，
改成更小的尺寸并没有解决问题 —— **别在这上面花时间**。

## 8. 最小可复现骨架

```python
import struct

MAGIC            = b"\x5a\xa5\x34\x12"
ID_LEN           = 10
TITLE_LEN        = 16
INDEX_ENTRY_SIZE = 16
INDEX_START      = 272

def build_face(title, face_id, files, preview_rgba, w=212, h=520):
    """files: [(name, data), ...]；name 形如 'lua/face_01.png'"""
    n = len(files)
    first_data_off = INDEX_START + (n + 1) * INDEX_ENTRY_SIZE

    # 1) 算每个文件项的偏移与 size
    entries, cur = [], first_data_off
    for name, data in files:
        nb = name.encode("ascii")
        size = 20 + len(nb) + len(data)      # 不含 padding
        entries.append((nb, data, cur, size))
        cur += size + (4 - size % 4) % 4
    data_end = cur

    out = bytearray()

    # 2) 文件头 64B
    out += MAGIC
    out += b"\x00" + bytes([ID_LEN])         # [4]=0, [5]=10 —— 两个独立字节
    out += b"\x00" * 10                      # [6-15]
    out += struct.pack("<I", 0x800)          # [16-19]
    out += b"\x00" * 8
    out += struct.pack("<I", 1)              # [28-31]
    out += struct.pack("<I", data_end)       # [32-35]
    out += b"\x00" * 4
    out += str(face_id).encode("ascii").ljust(ID_LEN, b"\x00")[:ID_LEN]   # [40-49]
    out += b"\x00" * 14

    # 3) Title 区
    out += b"\x00" * 40
    out += title.encode("ascii", "replace").ljust(TITLE_LEN, b"\x00")[:TITLE_LEN]  # [104-119]
    out += b"\x00" * 52

    # 4) 元数据区
    idx_end = INDEX_START + n * INDEX_ENTRY_SIZE
    out += struct.pack("<I", data_end)
    for v in (1, 256, 0):
        out += struct.pack("<I", v)
    for _ in range(4):
        out += struct.pack("<II", INDEX_START, 0)
    out += struct.pack("<I", n)              # [216] 文件数
    out += struct.pack("<II", INDEX_START, 0)
    for _ in range(3):
        out += struct.pack("<II", idx_end, 0)
    out += struct.pack("<II", 0, idx_end)
    out += struct.pack("<I", INDEX_ENTRY_SIZE)   # [268]

    # 5) 索引表 + 哨兵
    for i, (nb, data, off, size) in enumerate(entries):
        out += struct.pack("<HHIII", i, 0x0500, 0, off, size)
    out += struct.pack("<HHIII", n - 1, 0x0500, 0, 0, 0)

    # 6) 数据区
    for nb, data, off, size in entries:
        out += (len(data) & 0xFFFFFF).to_bytes(3, "little")
        out += bytes([len(nb)])
        out += b"\x00" * 16
        out += nb + data
        out += b"\x00" * ((4 - size % 4) % 4)

    # 7) 尾部位图
    out += b"\x00" * 4
    out += struct.pack("<HHI", w, h, len(preview_rgba))
    out += preview_rgba

    return bytes(out)
```

```
.fprj + app/lua/*.png|jpg + main.lua
        │
        ▼
```

## 11. AOD 息屏子工程（2026-10-01 实测）

工程里放一个**同级** `AOD/` 目录，主工程打包时会一并编入，**不单独编译**：

```
MyFace.fprj + images/ + app/lua/
AOD/
├── AOD.fprj          ← 目录名与文件名都固定
└── images/
```

`Compiler.exe` 内建这条路径（字符串表里有 `\AOD`、`\AOD\images`、`AOD face file is not found`），
不是第三方工具的约定。

### 11.1 AOD 屏**不支持 Lua**（实测）

往 `AOD.fprj` 里写 `Shape=34` 挂载点：

| 写法 | 结果 |
|---|---|
| `Name="app_lua%2Fmain.lua"` | 编译通过，但产物里**只有主屏那一份** `lua/main.lua` |
| `Name="app_lua%2Faod.lua"` + `AOD/app/lua/aod.lua` | 同上，`lua/aod.lua` **不入包** |

两种写法的产物**字节完全相同**（445 952 B），AOD 的 Lua 源码在产物里搜不到。
→ **AOD 只能靠 `Shape=30`（静态图）/ `Shape=32`（数字位图 + `Value_Src`）驱动。**

### 11.2 AOD 屏让布局整体后移

| | 无 AOD | 有 AOD |
|---|---|---|
| 头部 `[28]` 低 16 位（屏数） | `1` | `2` |
| **索引表起点** | `272` | **`360`**（元数据区 +88 B） |
| 索引表后的描述块 | 只有 1 条哨兵 | 多组记录，**哨兵在最后** |

> ⚠️ 因此**不能**再假设「首个文件项 offset == 索引表起点 + (N+1)×16」。
> 带 AOD 时索引表与文件数据之间还会夹一段描述块。校验器要用格式硬约束去定位
> （见 `tools/verify_face.py` 的 `find_index_start`），别抄偏移常量。

### 11.3 索引表之后的「描述块」

带 AOD 时这块按 tag 分成若干组同长记录：

| tag | 含义 | 备注 |
|---|---|---|
| `0x0000` | AOD 控件描述 | 条数 = AOD 屏的控件数，每条 16 B |
| `0x0200` | 预览位图 | 一条一个屏，`size` = 位图字节数 |
| `0x0300` | **位图数组** | AOD 的数字位图，`size` = 图宽 × 图高 × 4 × 张数 |
| `0x0700` | 小件 | 冒号这类 |
| `0x0500` | 哨兵 | 最后一条，`offset = size = 0` |

### 11.4 AOD 素材**不进索引表**

AOD 的位图直接躺在数据区之后，**没有文件名、没有索引条目**。
所以不能靠翻索引表判断 AOD 有没有生效，要看头部 `[28]` 的屏数与描述块。

### 11.5 AOD 的体积代价（逐项实测）

| 项 | 代价 |
|---|---|
| AOD 空屏 | +88 B |
| 每个 `Shape=30` 图片 | `宽 × 高 × 4 + 60` B |
| 每个 `Shape=32` 数字组 | `图宽 × 图高 × 4 × 图数` |

- `Shape=32` 的位图**按 BitmapList 去重**：多个控件引用同一张列表只付一次钱。
- 46×64 的时分数字（各 2 位，共用一张 11 图列表）≈ **127 KB**；20×28 的日期 ≈ **24 KB**。
- 默认不放全屏黑底 —— AMOLED 黑像素不发光，省下 431 KB。

> **主屏与 AOD 屏的 `Shape=30` 代价不一致**：主屏上的图片控件会被合成为整屏位图
> （+431 KB/个，与图片尺寸无关），AOD 屏按图片实际尺寸算。这个差异实测确认过，
> 不是笔误。

### 11.6 `Shape=32` 的数据源 ID（`Value_Src`）

编译器**只把数字原样存下、不校验语义**，由设备侧 dataman 在运行期解析。
手环 10（`DeviceType=466`）的 ID 表（节选，取自 Mi-Create 的 `sources.json`）：

| 数据源 | ID | 数据源 | ID |
|---|---|---|---|
| 时 0–23 | `0811` | 日 | `1812` |
| 时·低位 | `0911` | 月 | `1012` |
| 时·高位 | `1000911` | 年 | `0812` |
| 分 0–59 | `1011` | 星期（0=周日） | `2012` |
| 分·低位 | `1111` | 电量 % | `0841` |
| 秒 | `1811` | 心率 | `0822` |
| AM/PM | `0813` | 步数 | `0821` |

ID 是**十六进制字面量去掉 `0x` 与前导零**。官方手环 8 Pro 的 AOD 样本用 `Value_Src="811"`
显示小时，与本表 `0811` 一致。

### 11.7 `Shape=32` 的控件写法

```xml
<Widget Shape="32" Name="aod_hour" X="8" Y="190" Width="92" Height="64"
        Alpha="255" Digits="2" Alignment="1" Spacing="0" Blanking="0"
        Visible_Src="0" Value_Src="0811"
        BitmapList="aod_t_00.png|aod_t_01.png|…|aod_t_09.png|aod_t_00.png" />
```

- `Width = 单张数字图的宽 × Digits`、`Height = 单张数字图的高`
- `BitmapList` 官方样本给 **11 张**（0–9 再补一张 0），照抄数量最稳
- 生成实现见 `watchface-tool/watchface_tool/aod.py`

### 11.8 描述块与素材区的精确布局（2026-10-01 补齐，纯代码打包用）

这一节是把 AOD 产物**写出来**（而不只是读出来）所必需的。

**整体分段（带 AOD 时）：**

```
[0,172)      头部 + Title
[172,260)    主屏元数据      （22 个 u32 槽）
[260,360)    AOD 尾元数据    （25 个 u32 槽）
[360, 360+n*16)   索引表      ← 带 AOD 时**恒从 360 开始**，不是 272
[d0, descEnd)     描述块      d0 = 360 + n*16，16 B/条
[descEnd, filesEnd)  文件数据区
[filesEnd, assetsEnd) AOD 素材区   ← assetStart = filesEnd，无需再对齐（已 4 字节对齐）
[EOF-440972, EOF)    尾部预览位图  （12 B 头 + 212*520*4 BGRA）
```

**描述块每条 16 B：**

| 偏移 | 长度 | 字段 |
|---|---|---|
| +0 | 2 | `idx` |
| +2 | 2 | `tag` |
| +4 | 4 | `0` |
| +8 | 4 | `offset` —— **绝对偏移** |
| +12 | 4 | `size` |

`idx` 的语义**分类别不同**，这是最容易写错的一处：

- `tag 0x0000`（AOD 控件锚点）：`idx` = **控件序号**（即 `planAll()` 出来的下标）
- 其它所有 tag：`idx` = **该类自己的自增计数器**（0,1,2,…）

**描述块的组顺序固定为：**

```
锚点 0x0000（每个 AOD 控件一条）
  → 位图 0x0200
  → 位图数组 0x0300
  → 小件 0x0700
  → 哨兵 0x0500
```

**素材区的物理顺序又是另一套**（别和描述块顺序混了）：

```
锚点 → 小件(0x0700) → 位图(0x0200) → 数组(0x0300)
```

**各 tag 的负载：**

| tag | 长度 | 内容 |
|---|---|---|
| `0x0000` | 16 B | `u16 classIdx, u16 refTag, u16 anchorX, u16 anchorY, u32 0, u32 0`。`refTag` 是**被引用的那个控件**的 tag：`Shape=30` 给 `0x0200`（锚点 = 控件 X,Y）、`Shape=32` 给 `0x0700`（锚点 = X + 单字宽, Y） |
| `0x0200` | 12 B + 像素 | `u32 0, u16 w, u16 h, u32 len(= w*h*4)` |
| `0x0300` | 12 B + 像素 | `u8 0, u8 张数, u16 0, u16 w, u16 h, u32 len(= w*h*4*张数)`，**按 `BitmapList` 去重**，一个不同清单只出一条 |
| `0x0700` | 20 B | `Value_Src`(2 B 原始 hex) + `u8 digits` + `u8 0x16` + `u32 0` + `u16 数组下标` + `u16 0x0300` + `u32 0` + `u32 0` |
| `0x0500` | 16 B | `u16 (主屏文件数 - 1), u16 0x0500, u32 0, u32 0, u32 0` |

> ⚠️ **`offset` 一律是绝对偏移。** 写辅助函数按 tag 找"第一条记录"时，
> 很容易返回相对值 `k*16` 而调用方当绝对值用 —— 症状是所有 AOD 样本都在
> `@d0+16` 附近开始与参考产物对不上，且**差得一模一样**，看起来像"整段布局错了"。
> 正确的辅助函数签名应当是返回 `d0 + k*16`，并在注释里写明"返回绝对值"。

> 像素一律 **BGRA8888、直通（非预乘）alpha**。AOD 素材与尾部预览位图都是这个格式。
> 安卓端要注意：`Bitmap` 的 `ARGB_8888` 内部是**预乘**的，从透明画布读回彩色文字会污染结果，
> 正确做法是只往 `ALPHA_8` 掩膜上画，再乘目标色 —— 等价于 PIL 的"透明画布 + 单色填充"。
